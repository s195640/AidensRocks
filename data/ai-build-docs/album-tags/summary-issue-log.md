- **Migration:** `photoalbum_tags` table added to `createdb.sql` (fresh installs) and a new idempotent migration file (`CREATE TABLE IF NOT EXISTS`, existing/production installs). Also added to `pglogical.sql` (reference file) and `droptables.sql`, matching the pattern established for the last brand-new-table addition (`page_content`). - **Backend:** `GET /` (admin list) and `GET /:pa_key` (single album, used by the dialog's refresh) now return `tags: string[]`. `POST /` and `PUT /:pa_key` accept `tags` in the body, normalize it, and (inside a transaction) delete all existing tag rows for that album and reinsert the normalized set — skipping the insert entirely when the normalized set is empty.
- **Frontend:** `AlbumsCreateDlg.jsx` gained a "Tags" text input (comma-separated), pre-filled by joining the album's `tags` array, re-synced whenever `album.tags` changes (initial load or the dialog's own refresh button) without clobbering it in the middle of typing. On save, the raw text is split on commas and run through the same normalization rules as the backend before being sent. `AlbumsTable.jsx` got a new "Tags" column (comma-joined plain text — checked first for an existing badge/chip convention anywhere in the admin UI; there wasn't one, so went with the plan's own fallback rather than inventing a new visual pattern). `Albums.jsx`'s `handleCreate` now defaults `tags: []` so a brand-new album's dialog state always has an array to work with.

**Deviations from plan:**
1. The plan's backend guidance said "LEFT JOIN photoalbum_tags, aggregate... e.g. `array_agg(tag) FILTER (WHERE tag IS NOT NULL)`." Used a scalar subquery instead (matching the existing query's own established idiom for `first_image_name`/`first_image_media_type`, which are already fetched the same way): a direct `LEFT JOIN` against `photoalbum_tags` alongside the *existing* `LEFT JOIN Photos` would fan out — an album with, say, 5 photos and 2 tags produces 10 joined rows before aggregation, silently inflating `COUNT(p.p_key)` by the tag count and requiring `DISTINCT` in multiple places to compensate. A scalar subquery sidesteps this category of bug entirely. Verified directly: tagged a real album with 29 photos with 2 tags and confirmed `count` stayed `29` and `tags` had exactly 2 entries, no duplicates (see Issues/gotchas).
2. `GET /:pa_key` (single-album fetch) wasn't explicitly named in the phase doc, but needed the same `tags` addition — `AlbumsCreateDlg.jsx`'s refresh button calls this endpoint and does `setAlbum(albumRes.data)`, which would otherwise silently wipe `tags` from local state on refresh (the response object replaces `album` wholesale). Necessary for the feature to actually work through the existing refresh flow, not scope creep.

**Issues/gotchas encountered:**
- The join-fan-out risk above was caught during design, before writing the query, by comparing against the existing `COUNT(p.p_key)` — worth being aware of any time a second one-to-many relationship gets joined into a query that already aggregates one.
- Verified end-to-end against the local dev DB, not just build/lint: created a test album via the raw API with deliberately messy tag input (`["Main"," Featured","main","  ",""]`) and confirmed it normalized to `["featured","main"]`; confirmed `PUT` with a new tag set replaces the old one (delete+reinsert) and `PUT` with `tags: []` clears all tags; confirmed the count/duplication concern above against a real 29-photo album, then restored that album's tags to empty and deleted the test album afterward so no test data was left behind.
- Per the plan's own constraint note: front end and back end both independently implement the same normalization algorithm (trim/lowercase/drop-empty/dedupe) in two different files/languages — there's no way to literally share the code, so a test around this logic (confirming both produce identical output on the same messy input) would be genuinely valuable to have and to keep passing if either side's implementation ever changes. Not built, since no test suite exists in this repo and one wasn't requested — flagging per the plan's explicit ask.
- The phase doc's pglogical instructions were internally ambiguous about whether `replication_set_add_table` runs once (provider-side) or on both nodes — worded as "note that CREATE TABLE must be run identically on both prod nodes before this registration statement runs (also on both nodes)," which reads two ways. Wrote the migration file's comment following this session's established convention (provider-side, once) since that matches how pglogical replication sets actually work, but flagged the ambiguity explicitly in the file's own comment so you can correct it if this prod topology is actually bidirectional. Not resolved by testing, since the doc explicitly says not to run any of this against a live database.
