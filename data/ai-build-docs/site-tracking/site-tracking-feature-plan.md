# Site-Wide Tracking — Feature Plan

**Status:** Phases 1-4 built (2026-10-16). Phase 5 (retiring the old trackers) needs separate approval. Progress and deviations are in `summary-issue-log.md`. The panels went on a new Admin → Activity page instead of the Dashboard (asked and answered in phase 4).

## Why

Tracking today is five unrelated mechanisms, and most of them can't answer "what happened, when":

| What | Stored as | Dated? | Problem |
|---|---|---|---|
| Visits | `counter` + `counter_tracking`, one row per browser tab-session, posted by `Counter.jsx` on the **Home page only** | Yes | A visitor who lands on `/map`, `/photos`, a rock link or a Honoring Aiden entry and never opens Home isn't counted. No record of pages viewed after landing. |
| Song plays | `music.play_count` running total | No | Can't chart over time or tie to a visit. |
| Honoring Aiden views | `entry.view_count` running total | No | Same. |
| QR scans / bad links | `unmatched_path_hit`, one row per hit | Yes | `/qr` scans are logged as "unmatched paths" as a workaround. |
| Rock uploads | `journey_tracking`, one row per upload | Yes | A second copy of the same visitor fields. |

The goal is one dated, insert-only event log covering the whole public site. Every dashboard chart then comes from that log, including the second chart that started this ("music, Honoring Aiden and path hits together").

## Decisions so far

- **Record everything:** every page view; song plays and entry views; QR scans and rock lookups; actions (uploads, Request a Rock, contact, sign-up/sign-in, photo opens).
- **Gap review (2026-10-16) added:** outbound link clicks, music listening behavior, time spent on a rock's journey and what's opened inside it, following, per-email link tags, site errors, page load speed and scroll depth. Not added: All Rocks artist filter and full-screen photos, Map Filters use, media inside Honoring Aiden entries, the account flows beyond sign-up/in/out, and email opens (tracking pixels hurt spam scores and are often blocked). These can be added later as new event types without a schema change.
- **Visitor = device:** a random ID kept in the browser's `localStorage`. The same phone returning next week is one visitor with two visits. It holds no personal data and sets no cookie.
- **Start fresh:** the new log starts empty on ship day. The existing tables, counters and dashboard panels (Visitors by Day, Statistics, Music, Honoring Aiden, Path Hits) keep working unchanged alongside it. Retiring them is a separate, later decision.
- **Admins are counted but flagged:** activity while signed in as admin (level 50) is recorded with `is_admin = true`. The dashboard has an "Include admins" toggle, off by default.
- **Internal traffic is flagged too:** visits from the dev site or the home network are recorded with `is_internal = true` and get their own "Include internal" toggle, off by default.
- **Raw IP is kept**, along with the location lookup.
- **Events are kept forever.** No pruning.
- **Visit length is stored:** see "Visit length" below.
- **Form funnels:** Share Your Rock and Request a Rock each record opened → started → submitted, so the dashboard can show how many were opened but never submitted. See "Form funnels" below.
- **Both Visitors by Day charts stay** for now: the current `counter_tracking` one and the new one. The old one may be removed later.
- **Session:** 30 minutes without activity starts a new visit.
- **Error tracking (2026-10-16):** the goal is to know about every error a visitor runs into, without waiting for them to tell you. Everything in "Error tracking" below was approved: a crash screen, error messages shown to visitors, broken media, the 4xx replies that matter, slow requests, map tiles, server errors in the database, grouping with context and version, readable stack traces, and new/known/fixed status. Alerts: an email when a new kind of error appears, plus a daily summary.

## Data model

Two new insert-only tables. No `UPDATE`s and no counter columns, which fits the multi-master pglogical warning in `data/sql/migrations/add_app_version_table.sql`. Primary keys are UUIDs generated on the client, so two nodes can never collide and a resent batch is a no-op (`ON CONFLICT DO NOTHING`).

### `visit` — one row per session

| Column | Notes |
|---|---|
| `id` uuid PK | Session ID, generated by the client |
| `device_id` uuid | The visitor (localStorage) |
| `started_at` timestamptz | Server time of first sight |
| `landing_path` text | First page of the session |
| `referrer` text | `document.referrer`, or null |
| `ip_address` varchar(45) | From `req.ip` (server side, `trust proxy` already set). Not sent by the client, so the client-side `/api/ip` round trip goes away. |
| `geo` jsonb | `geoip-lite` lookup on the server, same shape as today |
| `user_agent` text, `platform` varchar | Platform derived on the server with `utils/platformFromUserAgent.js` |
| `screen` varchar, `language` varchar, `timezone` varchar | From the client |
| `client_version` varchar(50) | The site version running in the visitor's browser, from the build |
| `is_returning` boolean | Whether the device had a previous visit (the client knows this from its stored device ID) |
| `is_internal` boolean | Set on the server. True when the request comes from a private/loopback IP (`10.*`, `172.16-31.*`, `192.168.*`, `127.*`, `::1`) or its `Origin`/`Host` isn't the `PUBLIC_SITE_URL` host (the dev site). |

### `site_event` — one row per thing that happens

| Column | Notes |
|---|---|
| `id` uuid PK | Generated by the client |
| `visit_id` uuid → `visit.id` | |
| `device_id` uuid | Copied from the visit so per-visitor queries don't need a join |
| `created_at` timestamptz | Server receive time. The client's own time goes in `meta.client_ts`, because client clocks are wrong often enough. |
| `type` varchar(40) | See the catalog below |
| `path` text | Page the event happened on |
| `target_id` varchar(100) | What it was about: song `m_key`, entry slug, rock number, album id… |
| `meta` jsonb | Small type-specific extras |
| `account_id` int null | Signed-in account, resolved on the server from the bearer token |
| `is_admin` boolean | Set on the server from the account's level, never trusted from the client |

### Visit length

Kept without ever updating the `visit` row, so the tables stay insert-only:

- The client sends a `page_leave` event when a page is left or the tab is hidden (`pagehide` / `visibilitychange`). Its `meta.engaged_ms` is the time the page was actually visible, which excludes time sitting in a background tab.
- **Visit length** = `max(site_event.created_at) - visit.started_at`, computed at read time.
- **Engaged time** = sum of `engaged_ms`, computed at read time.
- The dashboard shows both, for example average visit length per day.
- A one-page visit with no `page_leave` (the browser was killed) has length 0, so averages leave it out.

Indexes: `(created_at)`, `(type, created_at)`, `(visit_id)`, `(device_id)`.

All the new tables (`visit`, `site_event`, and from "Error tracking" `server_error` and `error_group`) go in `createdb.sql`, `droptables.sql`, the numbered step files in `data/sql/migrations/0.15-site-tracking/` (see `DEPLOY.md`), and `pglogical.sql`.

## Ingest

- **Client:** a small `client/src/utils/track.js` module plus a `<SiteTracker />` mounted in `App.jsx`:
  - `device_id` lives in `localStorage`. The session is a `visit_id` that rolls over after 30 minutes without activity (also in `localStorage`, so it's shared across tabs). If storage isn't available, it falls back to in-memory IDs.
  - `track(type, { targetId, meta })` adds the event to a queue. The queue is sent every few seconds with `fetch`. On leaving the page (`pagehide`, the tab hidden, an outbound click), it's sent with `navigator.sendBeacon` instead: browsers drop a `fetch` started while a page unloads, even with `keepalive` (found in phase 3). A beacon can't send headers, so the sign-in token goes in the body and the server reads it from there.
  - Page views come from one `useLocation` effect, so no per-page wiring is needed.
- **Server:** `POST /api/activity` with `{ visit: {...}, events: [...] }` in `server/src/routes/activity.js`:
  - `optionalAuth` resolves `account_id` / `is_admin`.
  - It has its own rate limiter (not `publicCounterLimiter`, see the visitor-experience review), and each batch is capped (e.g. 50 events).
  - `type` must be in the allow-list. Strings are length-capped.
  - The visit is inserted `ON CONFLICT (id) DO NOTHING` on first sight, then the events are inserted, all in one transaction.
  - Known bot user agents are dropped. Most bots never run the JS anyway.
  - It always returns `204`. A tracking failure must never break the page.
- The admin section (`/admin/*`) isn't tracked at all. It's admin-only, and those page views would just be noise.

### Rock searches

There are three search inputs, and they behave differently:

| Page | Input | When it records |
|---|---|---|
| Track the Rocks (`TrackTheRocks.jsx`) | **Search** dialog | When Search / Enter is submitted with a valid number. `found` is set once the journey dialog finishes loading: true if the rock has a public journey. |
| Map (`RockMap.jsx`) | **Rock #** box (turns the matching pin green as you type) | Typing is live with no submit, so it records the value once typing stops for 1.5 seconds or the box loses focus. Only non-empty values that differ from the last one recorded count, so typing "1", "12", "123" records one search for 123. `found` = a pin with exactly that number is on the map. |
| Map | Rock number field in **Map Filters** | Same debounce rule. `found` = at least one pin matches the filter. |

- `input` is `search`, `highlight` or `filter`. `page` is `track_the_rocks` or `map`.
- Opening Track the Rocks from a shared `?rock=123` link records its own `rock_link` event, with `found` set the same way as a search. Those links mostly come from the family's emails. Links in emails carry `&from=email-follow` (Follow Rocks email, `buildRockJourneyLinkTag.js`) or `&from=email-response` (request response email, `buildRockNumbersWithLinksTag.js`). That was done 2026-10-16, ahead of the rest of this plan; the page ignores the parameter until tracking ships. It lets emailed links be told apart from ones people copied and shared. For those, the visit's `referrer` shows where the link was opened from when the browser sends one.
- Clicking a pin on the map is `map_pin`, not a search.

### Album viewing

Albums aren't separate pages: `Photos.jsx` (and `BirthdayAlbums.jsx` on the Birthdays page, which reuses the same components) swaps the album list for `PhotoCollection` in place. Page views alone can't tell which album was opened, so albums get their own timed events:

- **Opening an album** sends `album_open` with a new `open_id`.
- **Leaving it** sends `album_close` with the same `open_id`, its `engaged_ms` (time on screen, not counting time in a background tab) and how many photos were opened. That covers Back to albums, going to another page, and closing the tab. The last one is sent on `pagehide`, the same way as `page_leave`.
- **Each photo or video** shown in the lightbox sends `photo_view` with its own viewing time, sent when the slide changes or the lightbox closes. Moving through the lightbox (arrows, swipes, slideshow) counts each photo separately.
- If the browser is killed and no close event arrives, that album's view still counts as an open, but its time is unknown and left out of averages.

### Rock journeys

`rock_view` / `rock_close` work like albums: they share an `open_id`, and the close carries `engaged_ms` (on-screen time) and is also sent on `pagehide`. That gives time spent per rock. Inside the journey, opening a stop's location or comment and viewing journey photos or videos full-screen are recorded against the same `open_id`, so the dashboard can show what people look at once a journey is open.

### Music listening

Each `song_play` gets a `play_id`, and exactly one `song_stop` follows it with how long it actually played (`listened_ms`, not counting time paused), the song's length, whether it played to the end, and why it stopped. That gives listen-through rate and skips per song. The existing `play_count` keeps counting as before. If the browser is killed mid-song, the play still counts, but its listened time is unknown.

### Outbound links and contact

Clicks on links that leave the site are recorded before the browser navigates: the Facebook group (footer and Share Your Rock page), SUDC Donate, and the contact `mailto:`. Contact is a popup showing the contact email, not a form, so it records `contact_open` and, if the address is clicked, `outbound_click` with `mailto`. Whether an email was actually sent can't be known.

### Site health: page load speed

`page_perf` is sent once per visit, for the first page, from the Navigation Timing API (time to first byte, DOM ready, full load) plus Largest Contentful Paint (when the main content showed) where the browser supports it. Later in-app page changes aren't real page loads, so they aren't timed.

### Error tracking

The goal is to know about every error a visitor runs into without waiting for them to tell you. Today a rendering bug leaves a blank white page that nobody hears about, server errors only reach the Docker logs (about 116 `console.error` calls), and the error messages visitors see are never recorded.

#### What's captured in the browser

All of this is set up once in `SiteTracker` / `track.js`; only `error_shown` needs a call at each place an error message is shown.

1. **Crash screen (`render_crash`):** a React error boundary around the routes. Instead of a blank page, the visitor sees a gentle "Something went wrong" screen with a Reload button, and the crash is recorded with React's component stack (which component broke). There's a second boundary around the music player and the map, so a crash there doesn't take the whole page down.
2. **Uncaught errors (`client_error`):** `window.onerror` and `unhandledrejection`.
3. **Error messages shown to visitors (`error_shown`):** a `reportShownError(code, message)` helper, called wherever the site shows an error: All Rocks' load error, sign-in/sign-up/forgot/reset/verify errors, Request a Rock, My Rocks, Honoring Aiden entries, the rock-number alert on Track the Rocks, and the upload form. `code` is a fixed short name for that spot, so groups don't depend on the exact wording. Only our own message text is recorded, never what the visitor typed.
4. **Broken media (`media_error`):** one capture-phase `error` listener on `window` catches every `<img>`, `<video>`, `<audio>` and `<source>` that fails to load, site-wide. Leaflet tiles are split out as `map_tile_error` and collapsed to one event per page per tile server, with a count, so a map outage doesn't record hundreds of events.
5. **Failed API calls (`load_error`):** an axios response interceptor records:
   - network errors and timeouts,
   - any 5xx, including 502/504 from nginx when the server is down,
   - 429 (the visitor hit a rate limit), 413 (upload too large) and 408,
   - 400 on a POST/PUT/DELETE (a rejected submit).
   It skips 401/403 (signed out or not allowed, normal) and 404 (e.g. an unknown rock number). Admin API calls are skipped too.
6. **Slow requests (`slow_request`):** the same interceptor times every call. Anything over 10 seconds is recorded even if it eventually succeeded.

Every error event carries `app_version`, injected into the client at build time from the repo's `VERSION` file (Vite `define`), so an error can be tied to the release that was running in that visitor's browser. The visit row also gets a `client_version` column.

**Flood limits:** each distinct error (same fingerprint) is sent at most once per page, and at most 30 error events per visit. Known browser and extension noise is dropped, e.g. `ResizeObserver loop` messages and errors whose source is `chrome-extension://` / `moz-extension://`. Messages and stacks are truncated (2,000 characters for stacks, 500 for messages), and query strings are dropped from URLs.

#### Server errors (`server_error` table)

The server records its own errors in a new insert-only table. They don't come from a browser event, so they don't fit `site_event`:

| Column | Notes |
|---|---|
| `id` uuid PK | |
| `created_at` timestamptz | |
| `kind` varchar(20) | `request`, `background` (photo processing), `email` (a send failed), `process` (unhandled rejection) |
| `visit_id` uuid null | From an `X-Visit-Id` header the client adds to every API call. Links the error to the visitor's visit, so the dashboard can show what they did just before. |
| `account_id` int null | |
| `method`, `route` | E.g. `POST /api/rock-requests`, using Express's route pattern rather than the raw URL, so `/api/rock-posts/123` and `/api/rock-posts/456` group together |
| `status` int | |
| `message`, `stack` text | Truncated |
| `fingerprint` varchar(64) | See grouping |
| `app_version` varchar(50) | From `getAppVersion()` |
| `meta` jsonb | E.g. the rock number for a background failure |

How it's captured:
- A middleware records every response that finishes with a 5xx, whichever route's `catch` block sent it. That covers all the existing `res.status(500)` handlers without touching each one.
- The global error handler in `app.js` and `process.on('unhandledRejection')` record the actual error and stack.
- `processImagesInBackground` and `sendEmail` failures record through a shared `recordServerError(err, { kind, meta })` helper.
- Recording never throws. If the database itself is down, it falls back to `console.error`, as today.

#### Grouping and status

- **Fingerprint:** each error is grouped by a hash of its type plus a normalized message (numbers, UUIDs and quoted values replaced) plus its first stack frame (file and function), or, for API errors, plus method, route pattern and status. The server computes this at ingest; the client's value isn't trusted.
- **`error_group` table**, one row per fingerprint:
  - `fingerprint` PK, `source` (`client` / `server`), `type`, a sample `title`, `first_seen`, `status` (`new`, `known`, `fixed`), `status_changed_at`, `fixed_in_version`, `last_alerted_at`, `note`.
  - Counts, visitors affected and last seen are computed from the events at read time, not stored.
  - Unlike the event tables, this one is updated: by the admin changing a status, and by the alert job. Last-writer-wins on these columns is harmless, unlike a counter.
- **Status:** the admin marks a group `known` (seen it, not fixing yet) or `fixed`. Marking it fixed records the current version. If a `fixed` group happens again, it goes back to `new` and is alerted again.

#### Context for each occurrence

On the dashboard, each occurrence shows:
- when, page, platform/browser, app version, and the signed-in account if any,
- the visitor's last 10 events before the error (pages, clicks, searches), pulled from `site_event` by `visit_id`,
- for server errors linked through `X-Visit-Id`, the same trail plus the request that failed.

#### Readable stack traces

Production JavaScript is minified, so a raw stack reads `index-a1b2c3.js:1:48213`. The plan:
- Build with `build.sourcemap: 'hidden'`. This generates `.map` files without linking them from the code, so browsers never ask for them.
- The deploy copies the maps to a server-only folder keyed by version (`sourcemaps/<version>/`), so errors from older releases still resolve. nginx refuses to serve `*.map` from the public site.
- When the admin opens an error, the server translates the stack with the `source-map` package and caches the result. The dashboard shows real file names, functions and line numbers.
- Exactly where the maps live depends on how the client build reaches prod. This will be checked against `data/docker-compose/docker-compose-prod.yml` and `data/nginx/nginx.conf` during that phase.

#### Alerts

Two emails, through `sendEmail` and the existing email-template system:
- **New error:** sent when an error appears whose group is new, or was marked `fixed` and came back. At most one per group per 24 hours. It contains the title, type, page, platform, version, how many times and visitors so far, and a link to the dashboard.
- **Daily summary:** once a day (morning, in the site's timezone), only if there were errors in the past 24 hours. It contains each group's count and visitors, new groups first, and groups still `new` that nobody has looked at.
- Both are new templates (`error-new-email`, `error-daily-summary-email`), editable in Page Details. They're added to `ADMIN_RECIPIENT_SLUGS`, so they use the Send To address like the upload-failure emails.
- Errors from `is_internal` visits never trigger an email; they're still on the dashboard. Errors while signed in as admin do alert, since the family hitting a bug is real.
- **Only one node sends the daily summary:** prod runs two nodes, so the summary job runs only where `RUN_SCHEDULED_JOBS=true` is set in `.env`. There's no scheduler in the server today; this adds a small in-process daily timer. The new-error email is sent by whichever node received the error; in the rare case that both nodes see a brand-new error in the same instant, it could be sent twice.

### Scroll depth

No new event: `page_leave` carries `max_scroll_pct`, the furthest the visitor scrolled on that page, as a percentage of the page's height (100 for a page that fits on the screen). Content that loads after the page opens is handled by measuring against the page height at each scroll.

### Form funnels

The two main forms are both modals: Share Your Rock (`UploadRockForm`, opened through `UploadRockModalProvider`) and Request a Rock (`ContactReqestRocks`, opened from `FloatingRockLink` and from inside the upload form). Each one is a funnel keyed by form id, `share_your_rock` or `request_a_rock`:

- **Opened:** `form_open`.
- **Started:** `form_start`, the first time any field changes after an open.
- **Submitted:** `form_submit`, only once the server accepts the submission. A rejected submit records `form_error` instead.
- Each open gets its own `meta.open_id`, and the start/submit/error/close events for that open carry the same `open_id`, so each attempt can be followed even if the form is opened several times in one visit.
- **Abandoned:** an open with no `form_submit` for its `open_id`. Counted at read time, so it also catches people who close the tab with the form open, which never fires `form_close`. `form_close` is there for the breakdown, e.g. closed after starting vs closed without typing.
- No form contents are ever recorded: no names, emails, addresses or messages.

## Dashboard

New admin endpoints in `server/src/routes/statistics.js` (or a new `siteStats.js`). They're admin-only and added to `auth-matrix.test.mjs`. All of them take the same `range` / `tz` as `/api/statistics/daily`, plus `includeAdmins` and `includeInternal`.

1. **Visitors by Day** on the new data: visitors (devices), visits and page views per day, the existing By Platform view, and average visit length. It sits next to the current `counter_tracking` chart, which stays for now.
2. **Activity by Day** (the chart that started this): song plays, entry views, QR scans and not-found hits per day, one line each, with the same range buttons.
3. **Form funnels** for the range, one row per form: opened, started, submitted, abandoned, and submit rate, plus submitted vs abandoned by day.
4. **Albums** for the range: one row per album with opens, unique visitors, total and average viewing time, and photos opened, plus the most-viewed photos.

## Visitor-experience review (2026-10-16)

A review of the whole plan for anything a visitor could notice: speed, data use, behavior changes, things breaking. The rule throughout: **tracking is invisible and can never block, slow down or break anything a visitor does.** Each finding below is either a rule for the build or something already changed in this plan.

### Findings that needed a change

1. **Recharts made the public site heavier (shipped in 0.14.0, fixed in 0.15.10).** The app is one 3.9 MB JavaScript file (1.13 MB gzipped) that every visitor downloads, including all of `/admin`. Recharts added about 119 KB gzipped to it, roughly 10%, for a chart only admins see. **Fix:** lazy-load the admin section (`React.lazy` per admin route), so admin code and Recharts load only when someone opens `/admin`. This also takes the rest of the admin code out of the public download. Approved and done, see decisions below.
2. **Shared rate limit.** `publicCounterLimiter` is one limiter instance shared by site visits, path hits, song plays and Honoring Aiden views: 120 requests per 15 minutes per IP, across all four. If tracking used it, a busy visit would use up that budget and song plays and entry views would start getting 429s. Families on one Wi-Fi (or a group scanning QR codes at an event) share one IP. **Rule:** tracking gets its own limiter with a much higher cap, e.g. 1,500 per 15 minutes per IP. On a 429 the client stops sending for that page; it never retries in a loop.
3. **Ad blockers.** Blocker lists commonly block URLs containing `track`, `analytics` or `collect`. A blocked `/api/track` would fill visitors' consoles with errors and lose their data. **Rule:** the endpoint is `/api/activity`, with neutral names in the request too. Blocked or failed sends are swallowed silently.
4. **Tracking reporting itself.** The error capture records failed requests. If tracking's own sends went through axios, a tracking failure would record an error, which sends a request that fails again, and so on. **Rule:** tracking sends use `fetch` directly and never pass through the axios interceptor or `client_error`. The server's `recordServerError` never sends an alert email about a failed alert email.
5. **The existing axios interceptor.** `AuthContext.jsx` already has a response interceptor that signs out on 401. **Rule:** the new interceptor only observes. It re-throws the original error unchanged and returns successful responses untouched, so every existing `catch` block, retry button and the 401 sign-out behave exactly as today. The `X-Visit-Id` header goes only on same-origin `/api/` calls. All axios calls in the client are same-origin today, so it can't trigger a CORS failure.
6. **Dashboard queries slowing the public site.** The public site and the admin dashboard share one Node process and database. The existing `/api/statistics` loads every row into Node and counts in JavaScript, which blocks the server while it runs. On an event table that grows forever, "All" would get slower every month and stall visitors' requests while an admin looks at charts. **Rule:** every new dashboard query aggregates in SQL (`GROUP BY` on indexed columns) and returns only the summary rows.
7. **Crash screen sticking.** An error boundary that has caught a crash stays in its fallback until reset, so a visitor who navigates away would still see "Something went wrong". **Rule:** the boundary resets on every route change. The crash screen's wording is gentle, in keeping with the site, and matches the site's look.

### Rules for the build (no visible change)

- **Nothing waits on tracking.** No event is ever awaited before UI updates or navigation. Page views are queued after render. The queue is sent with `requestIdleCallback` (or a timeout where unsupported) every ~5 seconds, and only when there are events. Nothing is sent on a page sitting idle.
- **Outbound links are never delayed.** The click is queued and flushed with `keepalive` in the same tick, and the link opens normally. No `preventDefault`, no redirect through our server.
- **Leaving the page:** flushed on `visibilitychange → hidden` and on `pagehide` (iOS Safari doesn't reliably fire `pagehide`). `keepalive` requests are capped at 64 KB in flight, so batches are capped well under that.
- **Back/forward cache:** a page restored from the browser's back/forward cache (`pageshow` with `persisted`) counts as a new page view, and the tracker keeps working after the restore.
- **Scroll depth:** a passive scroll listener, throttled to one measurement per animation frame. No layout reads on every scroll event.
- **Music, map, lightbox, forms and the upload form:** tracking only reads state these components already have, or adds listeners next to existing handlers. No change to playback, map behavior, slides, validation or the chunked upload. Search debouncing is tracking-only; the inputs still update live exactly as now.
- **The broken-media listener** is passive and capture-phase, so it only observes. Images that fail today still look the same.
- **Storage:** if `localStorage` is unavailable (private mode, blocked storage), the tracker falls back to in-memory IDs and the site works normally. Every storage access is wrapped in `try/catch`.
- **No new dependencies in the public bundle.** `track.js` is plain JavaScript, a few KB. `source-map` is server-only.
- **Server:** `/api/activity` responds `204` as soon as the request is validated, and does the insert after responding. A slow or failing insert never holds up the visitor. `server_error` is recorded after the response finishes, so it never adds latency.
- **The old trackers keep running** (`Tracker` / `Counter` with `/api/ip` and `/api/location`, `PlayCountTracker`, the entry view bump, `NotFoundRedirect` / `QRRedirect` path hits). That's a few extra small requests per visit until they're retired in phase 5; no visible effect.
- **Email links:** `&from=email-follow` / `&from=email-response` are ignored by the page today. When tracking ships, the page reads `from`, records it, and leaves the URL alone, so a link someone copies still works.

### Testing for "no visible change"

- The whole regression suite (lint, API, browser) must pass unchanged at every phase. Existing tests are the check that nothing a visitor does behaves differently.
- New browser tests: the site works normally with `/api/activity` blocked (simulating an ad blocker) and with `localStorage` throwing. A forced crash shows the crash screen, and navigating away clears it.
- A build-size check: the public bundle must not grow by more than the tracker itself (a few KB). After the lazy-load fix it should shrink.
