### Follow-up fix (2026-07-06): chip components couldn't find UploadRockModalProvider
Your manual pass on `/share-your-rock` caught a real bug the build/lint checks couldn't have: `UploadRockButton`/`UploadRockLinkTrigger` threw `useUploadRockModal must be used within an UploadRockModalProvider`, plus a `createRoot() called on a container that's already been used` warning.

**Root cause:** `RichText.jsx`'s hydration pass (Phase 4) called `createRoot(node).render(<Component />)` for each chip mount point. `createRoot()` starts a **brand-new, fully disconnected React tree** — it has no access to any ancestor's context, since it isn't actually part of the surrounding component tree, just a DOM node that happens to be visually nested inside it. So the mounted `UploadRockButton` could never see `UploadRockModalProvider`'s context no matter where `RichText` itself was rendered. The `createRoot`-called-twice warning was a side effect of the same design: the effect re-runs when `usePageContent`'s fetch resolves (sanitized HTML changes from empty → real content), and the previous run's roots were being unmounted via a deferred `setTimeout`, racing the next run's `createRoot()` call on the same nodes.

**Fix:** rewrote `RichText.jsx` to mount chips via `ReactDOM.createPortal(<Component />, node, key)` instead of `createRoot`. A portal keeps the component in the real React tree (so context flows normally) while only teleporting its rendered DOM output into the sanitized-HTML container — this is the standard pattern for "render React content into a DOM node produced by dangerouslySetInnerHTML." Also eliminates the manual root-lifecycle bookkeeping (no more imperative `unmount()` calls, no more race condition) since React's own reconciler now owns the portal's lifecycle.

**Files changed:** `client/src/adminContent/RichText.jsx` only — the registry, provider, and chip components themselves needed no changes, since the bug was entirely in how RichText mounted them, not in what they do.
**Verified:** lint clean, build clean (2138 modules, same as before — no new imports needed, `createPortal` comes from `react-dom` which was already a dependency). Confirmed `createPortal` is exported from the installed `react-dom` version before relying on it, per this session's habit of checking installed-package APIs rather than assuming.
**Status:** Fixed, awaiting your re-check on `/share-your-rock` to confirm the button/link/Facebook chips now render and function correctly, and the console errors are gone.
